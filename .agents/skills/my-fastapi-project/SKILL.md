# my-fastapi: проектные правила Codex

Скилл адаптирован из CLAUDE.md этого репозитория. Он сохраняет договорённости разработки; текущие дефекты, количество тестов и результаты линтера проверяй по коду и запуску команд, а не по старому Status / TODO.

## Контекст и границы

Это учебный backend-проект на Python 3.14, FastAPI, Pydantic v2, async SQLAlchemy 2.0, asyncpg, PostgreSQL и Alembic. Работай в существующей архитектуре Repository + Unit of Work. Версии сверяй с pyproject.toml, uv.lock и .python-version; не обновляй зависимости ради следования слову «современный».

Пользователь учится backend-разработке. Объясняй существенный механизм и причину решения на языке пользователя. Вопросы «почему» и «как работает» отвечай без редактирования, если изменение не запрошено. Запрошенную реализацию выполняй в её объёме; при явном ограничении списка файлов соблюдай его. Учебный план не даёт разрешения сразу реализовать все будущие этапы.

## Основные договорённости

- Используй uv для зависимостей и запуска: uv add / uv add --dev / uv sync / uv run. Не заменяй его прямым pip или Poetry.
- Сохраняй цепочку router → service → UoW → repository. Роутер не работает с ORM/session напрямую. Сервис возвращает Pydantic-схему, созданную до закрытия UoW.
- Одна публичная операция сервиса открывает свой async with uow. Commit явный; выход откатывает незакоммиченную работу и гарантирует закрытие сессии.
- Не вкладывай вызов другого сервиса, открывающего тот же UoW, в уже открытый UoW: FastAPI кэширует зависимость на запрос, повторный вход заменяет session.
- Разделяй ORM-модели и схемы ввода/вывода. Идентификатор действующего пользователя берётся из авторизации. Публичный ввод не получает поля привилегий; PATCH изменяет только явно разрешённые поля.
- Сохраняй существующие доменные исключения, их HTTP-статусы/заголовки и общий обработчик. Не вводи параллельную систему ошибок.
- Собственная БД в сервисных/API-тестах — настоящий отдельный PostgreSQL. Подмена внешнего провайдера допустима через его интерфейс; mock-последовательности внутренних вызовов не являются целью теста.
- Секреты не выводи в ответы, логи или примеры с реальными значениями. Используй .env.example для структуры настроек, .env остаётся приватным.

## Что читать для конкретной задачи

- При изменениях API, сервисов, ORM, конфигурации, миграций или авторизации прочитай [правила backend](references/backend.md), затем затронутый путь в текущем коде.
- При изменении тестов или проверке backend-изменения прочитай [правила тестирования](references/testing.md), затем действующие conftest.py и тесты нужной функции.
- Для узкого объяснения читай только относящуюся к нему справку и код; не загружай весь проект без необходимости.

## Карта проекта

| Путь от корня репозитория | Назначение |
|---|---|
| src/main.py | FastAPI, lifespan, API-router, обработчики ошибок |
| src/api/deps.py | Composition root: UoW, сервисы, CurrentUserDep |
| src/api/v1/routes/ | HTTP-эндпоинты user, item, auth |
| src/core/config.py, security.py, uow.py | Настройки, JWT/пароли, транзакции |
| src/core/db/ | DeclarativeBase, ORM-модели, Pydantic-схемы, engine/session factory |
| src/repositories/, src/services/ | Запросы и бизнес-логика |
| alembic/ | Миграции; env.py получает DSN из настроек |
| tests/unit/, tests/integration/ | Чистая логика и проверки с Postgres/HTTP |

## Работа и проверка

Перед редактированием посмотри git status и относящийся к задаче diff. Сохраняй изменения пользователя. Проверяй реальные возможности установленной версии библиотеки по документации, когда это существенно для решения. Уже разрешённый пользователем поиск документации не требует повторного согласования.

Команды из корня проекта:

~~~text
uv run fastapi dev
uv run ruff check src tests
uv run ruff format --check src tests
uv run mypy src tests
uv run pytest tests/unit
uv run pytest
~~~

После изменений backend-кода выполни подходящие целевые проверки и полный pytest с тестовым Postgres. При недоступной БД выполни независимые проверки и явно сообщи, что интеграционные тесты не подтверждены. Не выдавай частичный прогон за полный.

Для изменения только инструкций/документации проверь формат, ссылки и фактические утверждения; запуск backend-тестов сам по себе не нужен. Не исправляй посторонние замечания линтера и не запускай массовое автоформатирование вне объёма задачи. Разделяй новые проблемы и существовавшие до изменения.

В результате кратко сообщи, что изменено, почему, какие проверки действительно выполнены и что осталось непроверенным. Если приводишь исполняемый пример, проверь его в изолированном окружении, когда это возможно, и укажи статус проверки.
