# Тестирование my-fastapi

Читай при изменении тестов или проверке backend-изменения. Сначала проверь текущие tests/conftest.py, tests/integration/conftest.py и tests/helpers.py: они определяют реальную настройку окружения.

## Расположение и зависимости

- pytest + pytest-asyncio; конфигурация pytest 9+ находится в [tool.pytest]. asyncio_mode=auto; fixture/test loop scope=session соответствует session-scoped engine и его asyncpg-соединениям.
- tests/unit проверяет чистую логику без БД и импорта приложения. tests/integration проверяет сервисы, репозитории и HTTP с настоящим PostgreSQL.
- Верхний conftest.py задаёт тестовые SECRET_KEY и POSTGRES_DSN до импорта src: переменные окружения перекрывают .env, а get_settings кэшируется.
- Общие хелперы, типы и константы находятся в tests/helpers.py. Не импортируй фикстуры из conftest.py в тесты.
- Используй реальную реализацию локальной зависимости, когда это возможно. Свою БД не заменяй fake/mocks. Внешние email/payment/API можно заменять fake за тем же интерфейсом; не связывай проверку с последовательностью внутренних вызовов.
- Fake должен воспроизводить существенное поведение заменяемой зависимости. У ORM defaults появляются при flush, а не обязательно при Python-конструировании объекта; это важно при моделировании данных.

## PostgreSQL и изоляция

- Тесты используют отдельную БД my_fastapi_test; guard требует DSN с суффиксом _test. Не ослабляй guard ради запуска на рабочей БД.
- Session-scoped синхронная фикстура migrated_db применяет Alembic upgrade head: async env.py запускает asyncio.run, поэтому не вызывай его внутри активного async-цикла.
- Engine живёт в пределах сессии тестов. На каждый тест выделяется connection с внешней транзакцией и последующим rollback.
- async_sessionmaker привязан к этому connection с expire_on_commit=False и join_transaction_mode="create_savepoint". Commit сервиса освобождает SAVEPOINT, не внешнюю транзакцию теста.
- Используется настоящий SQLAlchemyUnitOfWork. app.dependency_overrides[get_uow] подменяет фабрику; overrides очищаются после теста.
- Общий connection не моделирует независимые конкурентные транзакции. Для теста гонки проектируй отдельные сессии/соединения и собственную очистку тестовых данных.
- Не меняй async loop scope или изоляцию фикстур без понимания того, к какому loop и connection привязаны ресурсы.

## HTTP и подготовка данных

- AsyncClient использует ASGITransport и base_url с api_v1_prefix. Этот transport сам не запускает lifespan приложения.
- make_user регистрирует пользователя, логинится и возвращает auth headers. Login отправляется через data, а не json.
- Следуй фактическим путям роутов: лишний/недостающий trailing slash вызывает redirect, который httpx по умолчанию не следует.
- Состояние, недоступное из публичного API, например is_active=False, подготавливай через тестовый UoW.
- Для отдельного теста меняй настройки через monkeypatch.setattr(get_settings(), ...), чтобы изменение восстановилось после теста.

## Что проверять

- Поведение и бизнес-правила: чтение после записи; недоступность чужого объекта и сохранность данных; 404 после удаления; значения PATCH; каскад удаления пользователя и его items.
- Различай отсутствие поля PATCH, null для nullable поля и недопустимый null для ненулевой колонки.
- Для списков создавай данные нескольких владельцев; проверяй и наличие нужных, и отсутствие чужих/лишних записей. Одного happy path недостаточно для проверки изоляции.
- В auth проверяй одинаковый 401 и WWW-Authenticate для неверного пароля и неизвестного email; 403 для inactive только при корректном пароле; прекращение доступа после удаления/деактивации.
- В JWT проверяй собственные настройки: обязательные claims, подпись, срок, разбор sub. Не тестируй повторно внутреннюю реализацию библиотеки без собственной логики.
- Один негативный сценарий должен нарушать одно условие и падать по ожидаемой причине. Для регрессии покажи падение до исправления и успех после, сохраняя чужие изменения.
- Не копируй весь ответ или декларации схем в assert без необходимости. Проверяй поля, которые выражают контракт и правило задачи. Не добавляй тесты только ради покрытия строк или совпадения структуры кода.
- Называй тесты по наблюдаемому поведению: test_subject_condition_outcome. Для параметров используй осмысленные id.
- Открытый известный дефект при добавлении теста можно обозначить xfail с reason и strict=True; не прячь неожиданные падения под xfail.

## Проверка секретов

- Секретные ORM-колонки помечаются info={"secret": True}. После импорта моделей tests/helpers.py собирает SECRET_FIELDS из Base.registry.mappers и проверяет, что набор не пустой.
- Существующий response hook сначала читает response.aread(), затем проверяет отсутствие названий секретных полей в ответе. Сохраняй его при изменении HTTP-фикстуры.
- Этот guard дополняет выходные схемы и проверки поведения; он сам по себе не доказывает отсутствие утечки секретного значения под другим именем.
- Не используй assert на объекте-генераторе: он истинный сам по себе. Собери результат или используй all/any в соответствии с проверкой.

## Запуск и результат

- Только unit: uv run pytest tests/unit.
- Полный набор: uv run pytest; необходим доступный Postgres и отдельная тестовая БД. При необходимости создать её локально: docker compose exec postgres createdb -U user my_fastapi_test. Миграции применяет фикстура.
- После backend-изменения проверь стиль/формат/типы и полный набор. Если часть проверки заблокирована окружением, сообщи точную причину и фактический охват; не исправляй посторонние файлы ради чистого общего вывода.
- Изменение инструкций или Markdown не требует backend-тестов, если поведение приложения не менялось.
