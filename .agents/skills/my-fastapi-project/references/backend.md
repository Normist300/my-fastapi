# Backend: договорённости my-fastapi

Читай при работе с API, сервисами, данными, настройками и авторизацией. Это самостоятельные соглашения данного проекта; для других репозиториев учитывай их собственную архитектуру. Фактические имена и сигнатуры сверяй с текущими файлами.

## Слои и транзакции

- Роутеры в app/api/v1/routes валидируют вход, вызывают сервис и возвращают Pydantic. Не обращаются к session и ORM напрямую.
- Ресурсные URL — существительные во множественном числе; многословные сегменты в kebab-case, параметры в snake_case. Действия над текущим пользователем — /users/me. Литеральные пути с тем же HTTP-методом регистрируются перед параметризованными.
- Имена функций роутеров описывают действие и сущность, например `create_task`, `list_tasks` и `read_me`; учитывай их использование при генерации OpenAPI. При явно заданных operation_id сохраняй их уникальность и совместимость контракта.
- Интерфейсы имеют префикс `Abstract`, реализации — `SQLAlchemy` или `Fake`. Определяй границы репозиториев по операциям сервиса. Например, `GroupRepository` может работать с `Group` и `GroupMember`. UoW аннотирует специализированный интерфейс и создаёт реализацию на общей сессии.
- Общий репозиторий использует self.model. Специализированный запрос явно использует нужную ORM-модель; уникальный поиск возвращает scalar_one_or_none(). Аргументы — обычные Python-типы.
- Сервис зависит от `AbstractUnitOfWork` и задаёт порядок вызовов репозиториев. В рамках одной операции все репозитории используют одну сессию и транзакцию. Сервис явно вызывает `commit()`.
- SQLAlchemyUnitOfWork при входе создаёт session и репозитории. При выходе rollback выполняется в try, session.close — в finally. После явного commit последующий rollback не отменяет уже зафиксированное.
- Создавай сессию в SQLAlchemyUnitOfWork.__aenter__ через self.session_factory(close_resets_only=False). После close такая сессия не должна повторно начинать транзакции: это помогает обнаружить забытый async with uow, который иначе может скрываться за повторным использованием сессии после авторизации. При следующем последовательном входе UoW создаёт новую сессию; параметр не заменяет контекстный менеджер и гарантированную очистку ресурсов.
- Не открывай повторно общий UoW внутри уже выполняющейся операции сервиса. Приватные вспомогательные методы вызывай в пределах текущего блока без повторного входа.
- Преобразуй ORM-объект в выходную схему внутри UoW. Нужные связи загружай запросом репозитория, например selectinload; отложенный I/O после закрытия сессии недопустим.
- ORM-объекты создавай с явными полями вместо распаковки всей входной схемы. Для повторяющегося поиска можно использовать приватный async-хелпер «найти или выбросить исключение».
- Текущая сигнатура repo.delete(id) допустима: сервис предварительно проверяет существование/доступ; повторный get может использовать identity map. Переход на delete(obj) не является обязательным сопутствующим рефакторингом.

## ORM, схемы и PATCH

- Модели SQLAlchemy отделены от Pydantic. В Mapped указываются Python-типы; SQL-типы и настройки — в mapped_column. ORM и репозитории не зависят от Pydantic.
- Используется обычный DeclarativeBase, не MappedAsDataclass. У полей времени timezone-aware datetime; updated_at обновляется через onupdate при реальном UPDATE.
- При удалении пользователя удаляй его личные задачи и сохраняй созданные им групповые задачи. Если личные задачи удаляет сервис отдельным запросом, выполняй оба удаления в одной транзакции. При ревью проверь, может ли параллельное создание оставить личную задачу без автора. Сверяй правила удаления автора, исполнителя и группы с `ON DELETE` у внешних ключей и каскадами ORM, включая `delete-orphan`.
- UserRegister — публичная регистрация; UserCreate — административный ввод. UserPublic и UserRead различаются по аудитории. Не добавляй привилегированные поля в публичную схему ввода.
- Выходные ORM-схемы включают from_attributes=True. Существующие IDMixin/TimestampMixin/ORMReadMixin уже наследуют BaseModel; лишнее включение BaseModel в иерархию может сломать MRO.
- Для обновлений используй отдельную входную схему и применяй data.model_dump(exclude_unset=True) циклом setattr по полученным полям. PATCH-схемы различают отсутствующее поле и явно переданный null.
- Ответственность за состав допустимых полей обновления, их типы и валидацию полностью лежит на входных схемах. Схема должна исключать поля, которые клиент не вправе менять, включая owner_id и поля привилегий в публичном вводе; дополнительные входные поля не должны попадать в model_dump. Добавление поля в схему обновления означает разрешение на его изменение через эту операцию.
- Не дублируй поля схемы отдельным allow-list или явными присваиваниями в сервисе и не считай их отсутствие дефектом сервисного метода обновления. При ревью проверяй соответствие входной схемы правам операции.
- У ненулевого title явный null отклоняется валидацией; отсутствующее поле допустимо. У nullable description явный null очищает значение. Не реализуй PATCH как безусловное пропускание всех None.
- Перед заменой валидатора PATCH на новую конструкцию проверь поддержку в установленной версии Pydantic и сохрани различие между пропуском поля и явным `null`.

## Конфигурация и база данных

- Настройки находятся в app/core/config.py: BaseSettings, SettingsConfigDict(env_file=".env", extra="ignore"), get_settings с lru_cache. Не размещай общие настройки рядом с engine.
- debug по умолчанию False; включай его только локально. Отладочные ответы с traceback могут раскрывать внутренние данные клиенту. Реальные значения находятся в gitignored .env; .env.example содержит ключи и заглушки.
- secret_key и DSN с паролем — SecretStr. Разворачивай значение лишь на границе использования: jwt.encode/decode, create_async_engine. Входной пароль — SecretStr; парольная функция получает str; ORM хранит строковый хеш.
- Async driver — asyncpg. Engine использует pool_pre_ping=True, async_sessionmaker — expire_on_commit=False. Не подмешивай синхронные обращения к БД в async-путь.
- app/api/deps.py создаёт UoW обычной функцией get_uow, а не yield-dependency с неявным commit. Зависимости передаются через существующие Annotated-алиасы.
- Таблицы создаются миграциями Alembic. `env.py` получает DSN из настроек и передаёт `Base.metadata` как `target_metadata`. Импорт `Base` из `app.db.models.base` выполняет `app/db/models/__init__.py`. Этот пакет загружает модули ORM-моделей во время выполнения. Импорты под `TYPE_CHECKING` используются при проверке типов.
- После переноса или добавления ORM-моделей проверь в чистом процессе, что импорт `Base` тем же путём, что в `env.py`, регистрирует все нужные таблицы в `Base.metadata.tables`. Запускай `configure_mappers()` без подключения к БД после таких изменений, а также после изменения или удаления `relationship()` и переименования колонок, указанных в `foreign_keys`.
- Перед применением автогенерированной миграции проверь переименования и заполнение обязательных полей у существующих строк. Для создания схемы используй миграции Alembic.
- Команды миграций: uv run alembic current — текущая ревизия; uv run alembic revision --autogenerate -m "описание" — создать миграцию; uv run alembic upgrade head — применить; uv run alembic downgrade -1 — откатить один шаг. Создание, применение и откат требуют разрешения в рамках учебного режима. При Target database is not up to date сначала проверь выбранную БД и неприменённые миграции; не запускай upgrade автоматически только ради успешной автогенерации.
- В lifespan engine освобождается через dispose. Сохраняй единый api_router версии и префикс из настроек.
- Локальный Compose использует PostgreSQL 18 и volume /var/lib/postgresql. При смене major-версии проверь документацию образа. Локальный опубликованный порт должен быть ограничен loopback.
- Начальные POSTGRES_USER/PASSWORD/DB действуют при инициализации нового volume. Смена environment не меняет учётные данные уже созданной БД. Не удаляй volume ради настройки без явного разрешения на потерю данных.

## Ошибки и авторизация

- Сервисы выбрасывают DomainException и существующие специализированные исключения, а не HTTPException.
- HTTP status и необязательные headers находятся на классе доменного исключения; общий обработчик собирает JSONResponse с detail=str(exc). Это осознанная связь доменных ошибок с HTTP в данном проекте.
- Сохраняй понятные сообщения, согласованные параметры конструктора и типы. Обработчик регистрируется через app.exception_handler(DomainException); не добавляй вторую таблицу сопоставления статусов.
- AuthenticationError отвечает 401 и WWW-Authenticate: Bearer. Существующий UserInactive отвечает 403 в предусмотренных сценариях.
- Пароли хешируются pwdlib/Argon2; соль содержится внутри хеша. Не заменяй это на passlib и не добавляй отдельную колонку соли.
- JWT создаётся/проверяется в app/core/security.py через PyJWT с заданным алгоритмом, sub=user UUID и обязательным exp. Ошибки декодирования/UUID преобразуются в InvalidToken. Ключ подписи генерируется криптографически стойким генератором; при замене единственного ключа прежние токены перестают проходить проверку, поэтому учитывай это при смене конфигурации.
- Неизвестный email проверяется через DUMMY_HASH. Пароль проверяется до is_active; неизвестный email и неверный пароль имеют одинаковое публичное сообщение.
- Login использует OAuth2PasswordRequestForm: email передаётся в username, запрос form-data. Сохраняй текущий контракт; переработка authflow — самостоятельная задача.
- get_current_user повторно загружает пользователя из БД и проверяет is_active. Деактивация и удаление должны прекращать доступ по ранее выданному токену.
- В текущей реализации есть только короткий access-token; refresh/revocation не следует объявлять реализованными. Новая сессия/refresh/logout добавляются только в рамках соответствующей задачи.
- Для операций с задачами бери `user_id` из `CurrentUserDep`. Проверяй доступ при чтении и изменении задач, в том числе в списках и фильтрах.

## Логирование и наблюдаемость

- Используй стандартный logging. Настройка выполняется централизованно в app/core/logging_config.py; в модулях создавай logging.getLogger(__name__). Значения передавай отдельными аргументами сообщения; не настраивай handlers заново в каждом сервисе.
- HTTP-запросы логируются общим middleware в app/core/middleware.py: метод, шаблон маршрута, статус и длительность. Не дублируй эти сообщения в каждом роутере.
- Длительность измеряй через perf_counter с явными единицами. Указывай границы замера: получение ответа от call_next не означает завершение передачи потокового ответа или выполнения фоновых задач.
- В сервисах добавляй логи значимых бизнес-событий с нужными идентификаторами. Сообщения об успешном сохранении или удалении записывай после успешного commit. Такой лог подтверждает изменение данных, а не успешную доставку HTTP-ответа.
- Дополнительные логи обычного чтения добавляй, когда они дают полезный контекст сверх HTTP-лога. Не логируй каждый внутренний вызов.
- Ожидаемые доменные ошибки, например занятый email, отсутствие объекта или неверные учётные данные, не считай автоматически ERROR. Штатный rollback при выходе из UoW также не является ошибкой.
- ERROR используй для сбоев операций. CRITICAL — для проблем, из-за которых приложение не может продолжить работу или запуск. Не добавляй CRITICAL только ради использования этого уровня; сам вызов logger.critical не останавливает приложение.
- Не дублируй traceback одного исключения в repository, UoW, service и middleware. Учитывай действующее логирование Uvicorn. logger.exception используй внутри except там, где этот участок отвечает за запись ошибки.
- HTTP-статус 500 сам по себе не создаёт traceback. При стандартной настройке Uvicorn выводит traceback необработанного исключения; явно возвращённый ответ 500 такого исключения может не иметь. Текущий HTTP middleware записывает статус и длительность, но не traceback.
- При преобразовании известной ошибки БД в доменное исключение сохраняй причину через raise ... from exc. Проверяй конкретный тип ошибки и ограничение БД; неизвестные ошибки пробрасывай дальше, сохраняя traceback.
- Не записывай пароли, токены, хеши паролей, DSN, Authorization и полные входные данные. Проверяй также содержимое исключений и параметры SQL, которые могут попасть в traceback. Для связи сообщений одного запроса можно добавить request_id; не объявляй его реализованным без проверки кода.
- Разделяй логи и метрики. Prometheus требует отдельной инструментации; запись duration в лог не создаёт метрику. Для HTTP-метрик используй шаблоны маршрутов и ограниченный набор меток; UUID и request_id не используй как метки метрик. Длительность в метриках выражай в секундах. Избегай двойного учёта запросов собственным middleware и готовой инструментацией.
- Для контейнерного развёртывания предпочитай stdout/stderr и хранение средствами окружения. Учитывай оба потока, ротацию, срок хранения и сохранение многострочных traceback. Выбор сборщика и хранилища определяется задачей развёртывания; Loki, Alloy, Grafana и JSON-формат — возможные варианты, а не уже внедрённые компоненты или обязательные зависимости проекта.

## Стиль Python

- Абсолютные импорты от app; пакеты содержат __init__.py.
- Поддерживаются аннотации типов и mypy. Self — для методов, возвращающих собственный тип.
- В проекте на Python 3.14 используй PEP 695 generics, встроенные list/dict и объединения через |. Не добавляй from __future__ import annotations или строковые forward references без конкретной необходимости.
- Не переносись автоматически на новый major Python, SQLAlchemy, Pydantic или PostgreSQL. Поддерживай установленный стек и объём задачи.
